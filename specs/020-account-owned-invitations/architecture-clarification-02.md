# Architecture clarification 02: platform membership and invitation handshake

Date: 2026-10-20. Scope: `account-owned-invitations-v1`. Directed sequencing clarification; no new architecture audit or path expansion.

Approved architecture: `architecture.md`, SHA-256 `490eb8c361fc7cbdb60f3ae8d0b33843fb25c1c140a243df5e2a9f8294310ecb`.

## Assessment and boundary

The staged handshake below fits approved §§3–4, 7.2, 7.4–7.5 and 8.4. Those sections already assign platform provider work to Account's `EnsureProductPersonMembership` and `SendCompanyInvitation`, preserve live platform-account proof, require reciprocal links before projection, and reserve local role writes to the existing platform Actions after confirmed Account outcome. A provider membership confirmation and a later invitation are distinct existing side effects; they need not wait on invitation projection to return membership identity.

Inspected only the relevant approved paths: Account `EnsureProductPersonMembership.php`, `MapExistingProductPerson.php`; Compliance `GrantPlatformCompanyAccess.php`, `InviteCompanyAdministrator.php`, `AccountUserClient.php`, and the approved architecture. `RegisterCompanyPerson.php` is not required and remains outside this mutation scope.

This clarification applies to an explicitly authorized platform grant/invitation targeting the existing Compliance User selected/created by that platform write flow. It does not permit ordinary mapping or status synchronization to create identities, memberships, people or roles. Existing legacy people still require exact identity mapping; email collisions remain conflicts and cannot be adopted by this handshake. A new identity can be created only as the provider target of that explicit platform write, with persisted dispatch evidence and ambiguous-effect protection already required by §7.4.

## Concrete sequence

1. **Reserve stable platform intent in Compliance.** Existing platform Action authorizes current `PlatformAccess`, selects the exact company/local User, and stores an AccountRequestOperation with immutable actor_context `platform-account`, platform account ID, actor WorkOS ID, company binding, local person ID and target identity evidence. No admin role or success audit is added yet. The durable envelope, not a newly reconstructed current-User payload, is the retry authority.
2. **Ensure membership through Account.** Submit `person.membership.ensure` using that persisted UUID/hash and current platform proof. Account validates company binding, principal and fresh originating platform authority. It finds the exact known provider identity, or executes the explicitly requested new identity target where none exists without adopting by email; then finds/ensures exact-company membership. Persist each confirmed target separately. Already-dispatched uncertain identity/membership creation is not repeated blindly. Existing inactive membership is not silently reactivated by this clarification.
3. **Return a membership receipt independently of invitation projection.** Once identity and membership effects are confirmed, Account commits its ProductPersonLink for the supplied exact local person and stores a confirmed receipt identifying `local_person_id`, `shared_person_id`, `company_member_id`, `workos_user_id`, `workos_membership_id` and `membership_status`. Validate prior links for equality, including both member and local-person uniqueness; do not overwrite conflict. The membership operation has no invitation-send or invitation-projection target and does not wait on Compliance projection. Its confirmed state is not a claim that an email was sent.
4. **Persist the reciprocal identity before sending.** Compliance AccountUserClient validates the receipt envelope/company/actor/subject and all required confirmed IDs. In one short local transaction under the company/User/operation lock, verify the current local User and binding, reject a conflicting existing provider identity/link, set the previously absent provider identity from the confirmed receipt, persist/reconcile the exact PersonAccountLink and the durable membership receipt. No provider HTTP runs under this transaction. If the membership response is lost, retrieve/retry the same operation; if local persistence fails after Account commits, retry this step from the stored receipt. Never reconstruct a different membership envelope after learning the new provider ID.
5. **Perform the original local role write only after confirmed membership.** The existing platform Action rechecks current platform authorization, verifies the validated confirmed membership receipt plus exact reciprocal mapping, then adds the existing admin role and records its success audit. A pending/unknown/rejected membership, malformed receipt, mapping conflict or local transaction failure cannot grant the role or produce a success audit. This preserves the original platform grant responsibility; mapping/projection Actions never grant roles. Confirmed pending provider membership remains pending evidence and does not become active membership merely because the local role exists.
6. **If this was an invitation request, reserve a separate explicit invitation intent after step 4.** Existing InviteCompanyAdministrator/AccountUserClient creates a distinct durable `person.invite` operation bound to the same exact mapped member and platform actor. Store the prerequisite membership operation ID in its immutable payload or durable receipt context. The invitation operation has its own stable UUID and payload hash, derived from/persisted with the original platform invocation; it is not regenerated from the person's later invitation generation on retry. Account SendCompanyInvitation executes it under fresh platform proof and current membership/invitation checks. An already active membership/accepted invitation follows the existing no-send behavior; otherwise the explicit invite target may send once subject to uncertain-mutation protection. A grant-only invocation stops after step 5.
7. **Project the invitation after reciprocal mapping exists.** Account freezes the successful invitation snapshot and reserves its existing durable Compliance delivery target. Compliance applies it through ApplyInvitationObservation with existing generation/sequence guards. The membership receipt has already allowed reciprocal linking, so projection has no circular dependency. Product delivery failure remains separate from a successful provider invitation; retrying delivery never re-sends. Report invitation_sent only from confirmed provider evidence, and show pending/unconfirmed state honestly rather than fabricating a boolean success.

The existing entry Action can run these stages synchronously when each result is immediately confirmed and persist pending work otherwise; it must not promise a completed role grant or send while a prerequisite is unresolved. Existing bounded workers/recovery resume persisted operation IDs and confirmed receipts. No new endpoint, entity, permission, job class or configuration path is needed.

## Retry and concurrency constraints

- Keep the original membership operation UUID/hash after its payload's null provider identity becomes a known identity. A retry looks up the durable operation and stored envelope first; it does not hash current User fields into the old ID.
- Likewise preserve the exact invite intent across response loss and changed invitation generation. A genuinely new intentional resend is a new explicit user request only after the prior ambiguous outcome is resolved, not an automatic fallback.
- Lost membership response → same Account receipt; failed local mapping → replay local persistence of that receipt; lost invite response → same invitation operation/receipt; failed projection → delivery-target retry only. None of these paths clears dispatched markers or reopens confirmed targets.
- Duplicate/concurrent invocations for the same persisted platform intent converge under existing company/member/operation locks and uniqueness constraints. Reject identity/link conflict instead of using email or silently switching members.
- Revocation is checked for each new side effect and local role grant. Historical confirmed receipts remain evidence; they do not authorize the later invite/role write after privilege revocation.
